# «У Речушки» — интернет-магазин крафтового пива (полный проект)

Этот документ — основное описание проекта. Здесь описано, **что делает система, из чего она состоит, как запускается, как обрабатывает заказ, что было добавлено и исправлено**, а также как всё проверить своими руками.

> Вотермарка в интерфейсе сохранена без изменений: **Разработка сайта: Притчин Владимир, группа 9-прг401**.

---

## 1. Коротко: что стоит проверить в первую очередь

1. Запустить стек одной командой: `docker compose up -d --build`.
2. Открыть сайт <http://localhost/> — каталог, поиск, фильтры, корзина, оформление заказа.
3. Показать промокод `URE4KA` на главной и применить его при оформлении.
4. Зарегистрироваться с email `admin@urechki.ru` — сервер выдаст роль **Владелец**, откроется админка `/admin` и аналитика `/analytics`.
5. Открыть <http://localhost/status> — страница «Состояние сервисов» делает 10 реальных health-запросов к микросервисам.
6. Запустить мобильное приложение из папки `mobile` и показать экраны каталога, корзины, бонусов, промокодов и **Профиль → Состояние сервисов**.
7. Показать, что цену заказа считает **сервер**, а не браузер или телефон.

## 2. Назначение проекта

Проект демонстрирует полноценный учебный full-stack-продукт:

- **Сайт** — витрина и административная панель магазина.
- **Мобильное приложение** — те же данные и бизнес-процессы через отдельный мобильный API-шлюз.
- **Бэкенд** — набор независимых Spring Boot микросервисов, каждый отвечает за свою область.
- **Хранилища** — PostgreSQL для постоянных данных и Redis для кэша каталога.
- **Единая точка входа** — nginx отдаёт фронтенд и проксирует все `/api/*` запросы на нужные сервисы.

Проект намеренно сделан «живым»: данные для страниц и экранов берутся из API, а не из жёстко заданных массивов. Если остановить один микросервис, остальные продолжают работать; страница `/status` и одноимённый экран приложения показывают это наглядно.

## 5. Запуск

### Рекомендуемый способ — Docker

Нужно только установить и запустить **Docker Desktop**. Java, Maven и Node локально устанавливать не обязательно — всё соберётся внутри контейнеров.

В корне проекта (`D:\urechki-shop`):

```powershell
docker compose up -d --build
docker compose ps
```

Когда все сервисы станут `healthy`, откройте <http://localhost/>.

Полезные команды:

```powershell
docker compose logs -f                                  # все логи
docker compose logs -f order-service payment-service    # логи конкретных сервисов
docker compose restart                                  # перезапустить всё
docker compose down                                     # остановить, данные БД сохраняются
docker compose down -v                                  # остановить и удалить данные БД
```

При первом старте PostgreSQL выполняет `db/00-schema.sql` и `products.sql`, поэтому каталог автоматически заполняется товарами. Повторный старт не очищает данные, пока не выполнен `down -v`.

### Разработка сайта без Docker

Бэкенд должен быть поднят, затем:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

Сайт откроется на <http://localhost:5173>, а Vite проксирует `/api/...` на сервисы из Docker.

### Запуск мобильного приложения

Приложение находится в `mobile`, это **React Native + Expo без Expo Router** (навигация через React Navigation).

```powershell
cd mobile
npm.cmd ci
npm.cmd start
```

Для реального телефона в той же сети нужно указать IP компьютера с Docker:

```powershell
$env:EXPO_PUBLIC_API_ORIGIN = "http://192.168.1.10"
npm.cmd start
```

По умолчанию используется `http://localhost` — этого достаточно для Expo Web и эмулятора iOS.

Сборка веб-версии для проверки:

```powershell
cd mobile
npm.cmd run lint
npm.cmd run build:web
npx.cmd --yes serve@14 dist -l 19007
```

Затем открыть <http://127.0.0.1:19007>.

## 6. Как работает сайт

Фронтенд написан на React 19 + Vite. Все страницы загружаются лениво (`React.lazy`), поэтому начальный бандл небольшой. Глобальные провайдеры отвечают за тему, авторизацию, корзину и уведомления.

| Маршрут | Что делает |
|---|---|
| `/` | Главная: категории, популярные товары, быстрые действия, промокод `URE4KA` |
| `/catalog` | Поиск, фильтры по категории/цене/наличию, сортировка, сетка/список, pull-to-refresh |
| `/product/:id` | Описание, характеристики, похожие товары, добавление в корзину |
| `/checkout` | Трёхшаговое оформление: доставка → оплата → результат; сервер пересчитывает цену |
| `/profile` | Профиль, история заказов, избранное, бонусы |
| `/admin` | Управление товарами, остатками и статусами заказов (роль «Владелец») |
| `/loyalty` | Уровень, баллы, расчёт кэшбэка и скидки |
| `/track` | Отслеживание отправления по номеру заказа |
| `/favorites` | Избранное, синхронизируемое через `favorites-service` |
| `/analytics` | Сводка, воронка и последние события (только для «Владельца») |
| `/status` | **Состояние всех 10 микросервисов** в реальном времени |
| `/blog`, `/faq`, `/about`, `/production`, `/reviews`, `/contacts` | Информационные страницы магазина |
| `/roulette`, `/merch`, `/app` | Дополнительные демонстрационные сценарии |

Дополнительно на сайте есть командная строка поиска по `Ctrl/Cmd + K`, чат-помощник, cookie-баннер, прогресс прокрутки, адаптивная тёмная тема и понятные состояния загрузки/ошибок.

### Страница состояния сервисов

`/status` — не статичная картинка. Функция `checkPlatformServices()` параллельно отправляет 10 запросов:

```text
/api/products/health       /api/orders/health        /api/loyalty/health
/api/customers/health      /api/payments/health      /api/tracking/health
/api/notifications/health  /api/favorites/health     /api/analytics/health
/api/mobile/health
```

Каждая карточка показывает статус, время отклика и данные из ответа (например, количество товаров или заказов). Ошибка одного сервиса не ломает страницу: остальные карточки всё равно загружаются.

| Экран | Источник данных | Что делает |
|---|---|---|
| Главная | `/api/mobile/home` | Баннер, категории, популярные товары, тизер лояльности |
| Каталог | `/api/mobile/catalog` | Поиск, категории, постраничная загрузка, обновление/pull-to-refresh |
| Товар | `/api/mobile/product/{id}` | Описание, характеристики, избранное, выбор количества |
| Корзина / Оформление | `/api/orders`, `/api/tracking`, `/api/analytics` | Промокод, бонусы, адрес, способ оплаты, создание заказа |
| Заказы | `/api/mobile/orders/{id}` | История заказов клиента |
| Избранное | `/api/favorites` | Синхронизация с сайтом |
| Бонусы | `/api/loyalty` | Уровень, баллы, расчёт кэшбэка |
| Отслеживание | `/api/tracking` | Статус отправления и история событий |
| Акции | `POST /api/customers/promo/claim`, `GET /api/customers/promo` | 3 попытки в день, сервер выбирает приз и выдаёт промокод для заказа |
| Уведомления | `/api/notifications` | История сообщений |
| Аналитика | `/api/analytics` | Сводка, воронка, последние события |
| Недавно смотрели | локальный контекст | История просмотров товаров |
| О приложении | — | Возможности приложения и вотермарка |
| **Состояние сервисов** | 10 health-эндпоинтов | Та же проверка микросервисов, что и на сайте |

Важные детали:

- Приложение использует тот же бэкенд, что и сайт, но через `mobile-gateway-service`.
- Мобильный шлюз не хранит данные: он агрегирует ответы каталога, CRM, заказов, лояльности, избранного и аналитики.
- В шлюзе исправлен баг двойного URL-encoding: поиск по кириллице теперь возвращает корректные результаты (проверено: `COUNT=30 TOTAL=45`).
- Если нижестоящий сервис недоступен, `/home` и `/profile` всё равно возвращают HTTP 200 с полем `error` в соответствующем блоке — приложение не падает.
- В мобильном чекауте промокод и бонусы применяются к первой позиции заказа, потому что сервер считает скидку на один заказ.

## 8. Жизненный цикл заказа

Основной контракт:

```http
POST /api/orders
Content-Type: application/json

{
  "customerId": 2,
  "productId": 1,
  "quantity": 2,
  "promoCode": "URE4KA",
  "bonusSpent": 0,
  "paymentMethod": "Банковская карта"
}
```

> В запросе **нет поля `price` или `finalPrice`**. Даже если клиент его пришлёт, сервис заказов его не использует.

Что происходит на сервере:

1. **Валидация.** Проверяются `customerId`, `productId` и количество от 1 до 100.
2. **Получение данных.** Заказ обращается к `catalog-service` и `crm-service` внутри Docker-сети.
3. **Проверка остатков.** Если на складе меньше товара, заказ отклоняется.
4. **Расчёт цены.**
   - `basePrice = цена каталога × количество`;
   - скидка клиента из CRM (`discountPercent`), ограничена диапазоном 0–100%;
   - промокод из серверного справочника;
   - списание бонусов не больше баланса и не больше оставшейся суммы;
   - итог округляется по правилу банковского округления.
5. **Резервирование товара.** Остаток уменьшается до оплаты.
6. **Оплата.** `payment-service` получает сумму и ключ идемпотентности `order-{id}`. Повторный запрос с тем же ключом вернёт прежний результат, а не спишет деньги дважды.
7. **Успех или откат.**
   - при `SUCCESS` заказ получает статус **Оплачен** и номер транзакции;
   - при ошибке остаток возвращается, заказ помечается **Отменён**, клиенту возвращается понятная ошибка.
8. **Побочные действия.** Списание бонусов и отправка уведомления выполняются «best effort»: если эти сервисы недоступны, заказ не теряется, а проблема пишется в логи.

Статусы заказа можно менять через `PATCH /api/orders/{id}/status`.

### Пример проверенного расчёта

Для товара за 150 ₽, количества 2, клиента со скидкой 5% и промокода `URE4KA`:

```text
300,00 ₽  (база)
− 15,00 ₽ (скидка клиента 5%)
= 285,00 ₽
− 14,25 ₽ (промокод URE4KA 5%)
= 270,75 ₽ (итог, который вернул сервер)
```

Этот сценарий был проверен реальным POST-запросом, после чего тестовый заказ, уведомление и изменение остатка были удалены.

## 9. Бизнес-правила

### Роли и скидки

| Условие при регистрации | Роль | Скидка в CRM |
|---|---|---:|
| email `admin@urechki.ru` | Владелец | 10% |
| любой другой email | Клиент | 5% |

Роль и скидку назначает **сервер**. Поля `role`, `discountPercent`, `bonusPoints` из тела запроса при регистрации игнорируются. Обновление профиля тоже не позволяет изменить роль, скидку или email.

Email владельца настраивается переменной `APP_ADMIN_EMAIL` в `docker-compose.yml`.

### Промокоды

| Код | Правило сервера |
|---|---|
| `URE4KA` | −5% (основной промокод сайта) |
| `BEER5` | −5% |
| `BEER10` | −10% |
| `BEER15` | −15% |
| `CASH500` | фиксированно до 500 ₽, но не больше суммы заказа |
| `FREEDEL` | бесплатная доставка (правило интерфейса) |

Ранее сервис заказов игнорировал `URE4KA`, хотя код показан на главной странице и описан в документации. **Исправлено:** `URE4KA` приравнен к `BEER5` в методе `calculatePromoDiscount()`.

Рулетка выдаёт только коды, которые понимает `order-service`: `BEER5`, `BEER10`, `BEER15`, `CASH500`, `URE4KA`. Количество попыток хранится в памяти `crm-service` и ограничивается сервером (3 в день на email); приз зафиксирован в ответе, поэтому повторный запрос не меняет результат. История призов хранится в браузере.

### Бонусы

- Пользователь может потратить не больше своего баланса и не больше половины суммы после промокода (правило интерфейса).
- Сервер дополнительно ограничивает списание балансом и оставшейся суммой заказа.
- Дробные бонусы отбрасываются в сторону уменьшения.

### Уровни лояльности

| Уровень | Условие | Кэшбэк | Скидка уровня |
|---|---|---:|---:|
| Новичок | по умолчанию | 3% | 0% |
| Постоянный | оборот от 10 000 ₽ **или** 5 заказов | 5% | 3% |
| ВИП | оборот от 30 000 ₽ **или** 15 заказов | 8% | 5% |

Баллы считаются как `round(сумма × кэшбэк / 100)`. Повторный вызов `/api/loyalty/accrue` с тем же `orderId` не начисляет баллы повторно.

> Важно: в текущей версии цену заказа уменьшает **скидка клиента из CRM**, а уровень лояльности используется для расчёта кэшбэка, отображения баллов и истории начислений. Это разделено намеренно, чтобы сохранить самостоятельность сервисов.

### Доставка

Новое отправление создаётся со статусом **Собирается**, ориентировочной датой «через 2 дня» и первым событием в истории. Статусы меняет оператор через `PATCH`: `Собирается → Передан в доставку → В пути → Доставлен`. Прогресс в интерфейсе — условная шкала, а не реальные GPS-данные.

## 10. Безопасность и честные ограничения

Что сделано:

- Пароли хранятся в виде `sha256$соль$хеш`; сравнение выполняется в constant-time. Старые пароли открытым текстом при входе автоматически обновляются.
- Пароль никогда не возвращается в API-ответах (`CustomerResponse`).
- Роль, скидка и бонусы определяются сервером, а не клиентом.
- Цена заказа и итоговая сумма считаются только на бэкенде.
- Оплата использует `BigDecimal`, лимит суммы и ключ идемпотентности.
- Ошибки возвращаются в JSON с русскими сообщениями; стек-трейсы клиенту не отдаются.
- Health-эндпоинты есть у всех 10 сервисов; они используются и Docker healthcheck, и страницами состояния.

Ограничения учебного демо:

- Нет JWT/сессий: идентификация идёт по `customerId` в запросе. Это не продакшн-авторизация.
- CORS открыт для всех источников (`*`), чтобы локально работали сайт, Expo Web и телефон.
- Платёж и уведомления демонстрационные: реальные деньги и письма не отправляются.
- Транзакции платежей и история уведомлений хранятся в памяти сервисов и сбрасываются при перезапуске контейнера.
- `tracking-service` не получает статусы от реальных служб доставки.

### Добавлено в бэкенде

- 10 микросервисов вместо первоначальных пяти: лояльность, доставка, избранное, аналитика и мобильный шлюз подключены к общему Compose-стеку.
- Единые health-эндпоинты и Docker healthcheck у всех сервисов.
- Серверный расчёт скидок, промокодов и бонусов; источник цены — каталог.
- Резервирование остатков и компенсация при неуспешной оплате.
- Идемпотентность платежей и возврат.
- Агрегированный мобильный API с устойчивостью к падению downstream-сервисов.
- Аналитика по реальным сохранённым событиям, без выдуманных чисел.
- Атомарное изменение остатков через SQL-UPDATE: параллельные заказы не могут перепродать последнюю бутылку.
- Идемпотентность платежей через `computeIfAbsent` и проверку «отпечатка» суммы/способа; повторный возврат отклоняется.
- Уникальные ID уведомлений (`AtomicLong`), лимит длины сообщения и потокобезопасная очистка истории.
- Единый формат ошибок и логирование stacktrace в сервисах, которые ранее молча отдавали 500.
- Таймауты HTTP-клиента заказов (2–3 с), чтобы один зависший сервис не блокировал оформление.

### Добавлено на сайте

- Каталог с поиском, фильтрами, сортировкой, переключением сетки и обновлением данных.
- Карточка товара с характеристиками и похожими товарами.
- Корзина с прогрессом до бесплатной доставки и сохранением между перезагрузками.
- Трёхшаговое оформление с валидацией адреса и понятным результатом.
- Админка, страницы лояльности, отслеживания, избранного и аналитики.
- **Страница `/status`** с 10 реальными health-проверками.
- Локальные SVG-изображения: сайт не зависит от внешнего генератора картинок.
- Плашка промокода доступна с клавиатуры, с fallback-копированием и явным сообщением об ошибке.
- Количество в корзине ограничено 1–100, подписи кнопок учитывают название товара.

### Добавлено в мобильном приложении

- Полноценная навигация на React Navigation: 5 вкладок и stack-экраны.
- Экраны главной, каталога, товара, корзины, оформления, заказов, избранного и входа.

## 14. Хранение данных

- `products` — товары; создаются из `products.sql` при первом запуске БД.
- `customers` — клиенты, роли, скидки, бонусы, хеши паролей.
- `orders` — заказы, суммы, статусы, promoCode и transactionId.
- `loyalty_accounts`, `loyalty_transactions` — уровни, баллы и история начислений.
- `shipments`, `tracking_events` — отправления и события доставки.
- `favorites` — связь клиента и товара.
- `analytics_events` — сохранённые события для сводки и воронки.
- Redis — кэш каталога; очищается командой `docker compose exec -T redis redis-cli FLUSHDB`.

Схемы таблиц микросервисов создаются/обновляются автоматически через `spring.jpa.hibernate.ddl-auto=update`.

## 15. Публикация в интернет

Сайт нельзя выложить как обычную статику на GitHub Pages/Netlify: страницы берут данные через `/api/*`, а этот префикс проксирует nginx внутри Docker. Нужно публиковать весь стек.

### Вариант 0 — постоянно доступная облегчённая демо-версия

В папке `demo` лежит отдельная урезанная версия сайта: один контейнер на Node.js без внешних зависимостей, каталог на 164 товара, корзина, оформление заказа с подсчётом суммы на сервере, рулетка с лимитом 3 попытки в день и страница состояния. Она занимает около 50 МБ и помещается в бесплатный контейнер на 512 МБ.

Локальный запуск:

```powershell
docker build -t urechki-demo -f demo/Dockerfile demo
docker run -p 7879:7860 urechki-demo
```

Публичный адрес демо: <https://urechki-demo-ed615.containers.snapdeploy.app>. Бесплатный контейнер засыпает после 15 минут без посещений и просыпается при первом открытии страницы (до минуты). Полноценная версия с десятью микросервисами требует VPS или платного тарифа — см. варианты ниже.

### Вариант А — быстрая демонстрация без сервера

На компьютере с запущенным Docker:

```powershell
docker compose up -d --build
npx.cmd --yes cloudflared tunnel --url http://localhost:80
```

Cloudflare выдаст временный адрес вида `https://xxxx.trycloudflare.com`. Он открывается из любого браузера, HTTPS уже настроен, домен и VPS не нужны. Пока компьютер включён, работают сайт, все API и страница `/status`. Для Expo Web и реального Android укажите этот адрес в `EXPO_PUBLIC_API_ORIGIN` (см. `mobile/README.md`).

### Вариант Б — постоянная работа 24/7

1. VPS с Docker (Hetzner, Timeweb, Oracle Free Tier), открытые порты 80 и 443.
2. `git clone` репозитория и `docker compose up -d --build`.
3. A-запись домена → IP сервера.
4. HTTPS: установить Caddy и взять готовый конфиг из `deploy/Caddyfile`, заменив `example.com` на свой домен. Caddy сам получит сертификат Let's Encrypt и будет проксировать на локальный nginx.

Для хостингов, которые разрешают только один контейнер без `docker compose`, есть `Dockerfile.fullstack`: он собирает все 10 микросервисов, фронтенд, PostgreSQL, Redis, nginx и supervisord в один образ. Запуск: `docker build -f Dockerfile.fullstack -t urechki . && docker run -p 7860:7860 urechki`. Такой образ подойдёт, например, для Hugging Face Spaces, но платный план PRO: на бесплатном аккаунте Docker-пространства недоступны. Бесплатные контейнерные сервисы с 512 МБ ОЗУ (Render, Koyeb, SnapDeploy) не подходят — для 10 JVM и БД нужно не меньше 2–4 ГБ. Корневой `Dockerfile` специально оставлен облегчённым: он собирает демо-версию из папки `demo` с контекстом сборки `.` и используется для постоянного бесплатного демо.

### Что проверить перед публикацией

- Контроллеры пока разрешают `CORS: *` — для прода сузьте до домена сайта.
- Платежи демонстрационные: реальные деньги не принимаются.
- Админка `/admin` и ADMIN API не имеют авторизации — закройте их basic auth или firewall.
- Пароли и ключи в `docker-compose.yml` — демонстрационные, замените их на секреты.
